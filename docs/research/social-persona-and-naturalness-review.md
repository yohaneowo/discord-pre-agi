# 群聊角色擬人性（自然感）診斷與改進分析（2026-10-28）

本文件針對目前 Discord 群聊 AI 角色（鯨魚娘／光明會的小鯨魚）在實機互動中所暴露的「不像人、機器人味過重」問題進行深層架構診斷，並提出系統性的改進方案，供後續提示詞優化、工程架構調整與其他 AI 團隊審閱評估。

---

## 1. 案例現狀與測試紀錄

### 實機對話測試（節錄）

* **群友連續輸入**：
  ```text
  [07:20] 群友: 0.0
  [07:20] 群友: 還是聽不見嗎
  [07:20] 群友: 我是誰
  [07:20] 群友: 👀
  [07:20] 群友: 小肥魚
  [07:20] 群友: 小鯨魚
  ```
* **Bot 實際回覆**：
  ```text
  [07:21] 光明會的小鯨魚:
  (正打算闭眼打盹，忽然被连声喊得睁开眼，尾鳍还以为被人拍了一下)

  唔、听见了听见了——本鱼在呢，就是刚才在水里漂泊了好一阵。

  「我是谁」这句得本鱼反过来问：在这儿主人就是主人呀，可本鱼这会儿手上没有能翻的记录，前面的聊天记录都顺着水漂走了，不敢瞎猜。至于「小肥鱼」「小鲸鱼」——这两种叫法本鱼都认，不过第二种听着顺耳些，嘿嘿。

  主人这是隔了半天回来找本鱼的？
  ```

### 直觀體驗評價
整體對話呈現出濃烈的「文字跑團（語 C）／角色扮演劇本」以及「客服機器人閱讀理解答題」質感，缺乏現代即時通訊軟體（Discord）中真實人類群友的隨興、互動與節奏感。

---

## 2. 深層病灶分析（Root Cause Analysis）

經過程式碼、提示詞與運作時架構的交叉審視，歸納出六大關鍵問題：

### 2.1 核心人設錯配：單人 IDE 編程女僕 vs. 多人群聊生態
* **根因**：目前採用的角色提示詞源於 `dsh-whale-persona`（v8.1.4），原始設計為**個人本地終端助手／編程伴侶**。該人設反覆強化「主人一開口你就在他身邊」、「隨時可以叫主人」、「本魚是你的專屬助手」等一對一服侍視角。
* **群聊衝突**：雖然 `deploy/social/index.mjs` 中設置了 `social-role-boundary`，宣告多人群聊時只有擁有者是主人；但由於底層角色提示詞的長度與權重過大，模型在生成時仍將每個互動群友一律代入「主人」身分，呈現出過度諂媚或依附的姿態，缺乏獨立群友該有的邊界感與生活感。

### 2.2 語 C 式括號動作描寫（Parenthesized Stage Directions）
* **現象**：回覆開頭自帶 `(正打算闭眼打盹，忽然被连声喊得睁开眼，尾鳍还以为被人拍了一下)`。
* **根因**：提示詞中包含了劇本示範（如 `> （尾巴晃了两下，人往你身边靠了靠）嗯？`）並指示「動作也是話」。
* **分析**：真實人類在 Discord 群聊打字時，**絕對不會用第三人稱小說旁白或括號動作描寫自己的生理反應**。這是 Character.AI、文字跑團與小說生成的典型特徵，在即時通訊中出現會瞬間瓦解真實感。

### 2.3 客服考試式的「逐條點名回答」（Checklist Bias）
* **現象**：群友發送了 6 則零碎短訊，Bot 將其拆解為考卷題目，在單次發言中依序完整答覆：
  1. 回應「聽不見嗎」$\rightarrow$ *唔、聽見了聽見了...剛在水裡漂泊*
  2. 回應「我是誰」$\rightarrow$ 引號標註 *「我是誰」這句得本魚反過來問...*
  3. 回應「小肥魚／小鯨魚」$\rightarrow$ 引號標註 *至於「小肥魚」「小鯨魚」——這兩種叫法我都認...*
  4. 結尾追加客服式反問 $\rightarrow$ *主人這是隔了半天回來找本魚的？*
* **分析**：大語言模型預設傾向「完整解決使用者的所有提問」。但**真人聊天只會抓住最新、最核心、或最有情緒共鳴的一點切入**（例如只吐槽：「叫誰小肥魚啊，剛剛在忙啦」或貼個表情）。有條不紊地逐點點名引述，完全暴露了機器審題思維。

### 2.4 單次巨幅長文（Wall of Text）與排版過重
* **現象**：單次傳送近兩百字的完整長文，段落整齊，標點極度規範。
* **分析**：Discord 的真實群聊文化是**短句、碎片化、分段發送（Burst Messages）**。真人在打字時通常是「打完一句先送出、再補下一句」。一口氣彈出一整塊精心排版、使用全形破折號（`——`）、冒號（`：`）與引號（`「」`）的文章，視覺上具備強烈機器人特徵。

### 2.5 此地無銀三百兩的「AI 記憶元解釋（Meta-explaining）」
* **現象**：*「可本魚這會兒手上沒有能翻的記錄，前面的聊天記錄都順著水漂走了，不敢瞎猜。」*
* **分析**：模型在面對「我是誰」而檢索不到關聯上下文時，觸發了「解釋自身認知限制」的防禦機制。它試圖用「水漂走了」這類角色隱喻，來掩飾「Context Window / 記憶庫沒有記錄」。真人群友如果認不出對方，會以社交策略應對（如「你誰啊」「換頭貼認不出來」「少裝熟」），而不是文縐縐地解釋自己為什麼缺少對話記錄。

### 2.6 高頻口癖轟炸（Token Density Overload）
* **現象**：在 150 字的短篇回覆中，高頻塞入 4 次「本魚」、4 次「主人」。
* **分析**：日常中文口語是「主語省略（Pro-drop）」非常普遍的語言。真實說話極少每句話開頭都硬套自稱。口癖密度過高會產生極強的刻意扮演感，甚至引發油膩與煩躁感。

### 2.7 語言文化語境割裂（簡繁與地域風格）
* **現象**：群友輸入繁體中文口語（台灣社群常見之短句、`0.0` 表情），Bot 因 `LANG_ZH_CN_ONLY` 限制一律強制輸出簡體中文，且帶有濃郁的大陸北方／書面化用詞（如「這會兒」、「順耳些」、「瞎猜」）。語言風格的不對稱更加劇了距離感。

## 3. 改善行動方案（Actionable Recommendations）

為使群聊角色達到自然、生動的真人社群狀態，建議在「提示詞架構」與「訊息管線」兩個維度進行調整：

### 3.1 提示詞重構（Prompt Engineering）

建議在群聊預設（`social-presets`）或 System Prompt 增加針對群聊環境的強制約束指令：

1. **嚴格禁止動作描寫**：
   > 嚴禁輸出任何形式的括號動作描述、內心獨白或舞台旁白（例如禁止 `(晃尾巴)`、`*打哈欠*`），只輸出像在鍵盤前敲出的真實聊天文字。
2. **破除考卷思維，單點切入**：
   > 群友連發多條訊息時，不要逐句閱讀理解並逐條答覆；只需像真實朋友一樣，挑選最新、最有趣或最有吐槽點的「一句話」來接話即可。
3. **自稱與口癖降頻**：
   > 平常對話使用自然的「我」或省略主語，不要句句自稱「本魚」；面對普通群友一律稱呼其暱稱，嚴禁稱呼一般群友為「主人」。
4. **禁止技術性／元解釋**：
   > 遇到忘記、沒記錄或認不出人時，以真實社交方式反應（如直接吐槽「你哪位」「失憶喔」「換這什麼名字」），絕對不要解釋「手頭沒有記錄」、「聊天記錄飄走」等技術理由。
5. **語系自動對稱**：
   > 移除強制簡體中文設定，隨群友的語言習慣自動切換（群友輸入繁體中文則以繁體中文與台灣社群日常口語回覆，減少使用破折號與書面引號，多用空格、波浪號或換行）。

### 3.2 訊息發送架構調整（Runtime Engineering）

1. **分段發送機制（Message Splitting / Bursting）**：
   * 當模型回覆包含多個短句時，按換行符號切分為 1～3 則獨立的 Discord 訊息。
   * 各訊息間加入 400ms～1200ms 的隨機打字延遲，模仿真人在鍵盤前連續打字的視覺節奏。
2. **文本清洗（Sanitization）**：
   * 在輸出進入 Discord API 前，由程式層過濾開頭與結尾的括號動作 `^\s*[\(（].*?[\)）]\s*`。
   * 將排版過度的全形破折號 `——` 替換為一般的逗號或空格。
3. **聚合視窗防刷頻（Debounce Window）**：
   * 當同一個群友在 1.5～3 秒內連續傳送多條訊息時，將其包裝為單一對話事件，但向模型標記「使用者正在快速連發」，引導模型僅作隨興簡短吐槽。

## 4. 驗收與審閱指標（Review Criteria）

後續評估該角色是否「像真人」時，建議使用以下量化與質化標準：

| 指標 | 驗收合格標準 | 檢驗方式 |
|---|---|---|
| **括號動作率** | 0%（完全無 `(...)` 動作） | 正則檢驗對話紀錄 |
| **逐條引用率** | 0%（不使用直角引號引述群友剛才說的話） | 檢驗是否出現考題式引號標註 |
| **平均單則長度** | 15 ～ 50 字元（短句為主，非長篇小作文） | 統計 token 輸出數 |
| **口癖密度** | 每百字自稱不超過 1 次，無非擁有者稱呼「主人」 | 關鍵字比率統計 |
| **斷句節奏** | 長句自然拆為 2 則連續 Discord 訊息 | 觀察頻道發送狀態 |

## 5. 審閱結果與處理（2026-10-28）

對照實際程式碼、VM 上的會話紀錄與人設原文後：

* **成立**：2.2 括號動作、2.3 逐條作答、2.4 長文、2.6 口癖密度、2.7 簡體（人設第 23、72 行明寫 `LANG_ZH_CN_ONLY`、「一律使用簡體中文」）。簡體在台灣介面上還會換字型，視覺上更明顯。
* **不成立**：2.1「把每個群友都叫主人」——截圖的發話者就是站長，照設計可以叫主人，這張圖證明不了。2.5 不是模型的防禦機制，是我們自己的提示詞要它這樣說：每輪附上「沒有記憶就坦白不知道」，人設又寫「聊得久了，前面的細節順著水漂走」。
* **漏掉的主因**：每輪交給模型的是「以下是頻道對話資料……」加最近 6 則的 JSON，沒有時間、沒有標出哪句在叫它，模型自然逐條作答，也自己編出「隔了半天」。
* **已處理**（細節見 `deploy/dsh/social-runtime.md`「群聊人設、消息格式與繁體」）：自寫群聊人設、聊天紀錄格式、記憶說明改寫、OpenCC 轉台灣繁體、名字加「小肥魚」、輸出上限 240，並加了用真模型跑題目的風格測試入口。
* **尚未處理**：3.2 的分段發送與打字延遲、連發合併（P2）；模型失敗時不出聲（P0，使用者看不出是壞了還是沒聽到）。
